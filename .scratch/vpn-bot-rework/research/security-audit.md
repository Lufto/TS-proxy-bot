Ответ на задачу `issues/21-audit-bezopasnosti.md`, первая часть (проверка **решений**). Дата: 2026-10-21.

Что прочитано: `map.md`, все задачи 01–21, `research/` (ЮKassa и Stars, Remnawave, остальные платёжки), `docs/python-rules.md`, `docs/server-setup.md`, `docs/remnawave-upgrade.md`, `docs/checklist.md`, `GLOSSARY.md`, `CLAUDE.md`, `.gitignore`, набросок `bot.py` и `rem.py` (только устройство, значения секретов не копировались). Код не запускался, запросов к панели и платёжным API не было, на сервер не заходили. Поэтому всё, что касается **текущего состояния сервера и панели**, помечено «проверить при разведке».

Секреты в этом документе называются только по имени переменной. Значений здесь нет.

## Как читать

- **Серьёзность** — насколько плохо, если случится: **критический** (деньги, захват бота или панели, все клиенты), **высокий** (заметный ущерб, платящие клиенты без доступа), **средний** (неприятно, исправимо), **низкий**.
- **Вероятность** — насколько это реально для маленького сервиса примерно на 30 клиентов: высокая / средняя / низкая.
- **Меняет решение?** — «нет» значит, что мера ложится в уже принятые решения, её надо просто сделать при разработке. «Да» значит, что нужно согласие владельца. Номер — задача, где лежит решение.

## 1. Коротко: главное

1. **Webhook Telegram без секретного заголовка** — любой, кто узнает адрес, шлёт боту «сообщения» от имени любого Telegram ID, **включая администраторов**. Это полный захват админки. Лечится одной настройкой `secret_token`. (R01)
2. **Двойное начисление и «оплачено, но не выдано».** Оплату засчитывают три пути сразу: уведомление ЮKassa (повторы до 24 часов), кнопка «Проверить оплату», фоновая проверка. Действие Remnawave `extend` не идемпотентно: падение между «продлили» и «записали, что продлили» даёт второе продление при повторе. Нужны атомарный переход статуса заказа и продление на **заранее рассчитанную дату**, а не «+N дней». (R02)
3. **Вебхуки Remnawave теряются**: панель повторяет отправку всего 3 раза с паузой 5 секунд. Перезапуск бота при деплое, и событие «подписка истекла» потеряно навсегда. Платящий клиент не получает льготный период, а пробный период не продлевается. Нужна периодическая сверка с панелью, а не только проверка при старте. (R05)
4. **Панель Remnawave — самая ценная цель**, и сейчас её, скорее всего, видно в обход Cloudflare: настоящий IP сервера публичен из-за записей «DNS only». Захват панели означает все клиенты, все ссылки и все ноды. Плюс Docker обходит файрвол `ufw`. (R03, R09)
5. **Старые токены** бота и Remnawave лежат открытым текстом в `bot.py`, `rem.py` и в журналах сессий Claude Code на Mac. Файлы не внесены в `.gitignore`, а скоро появится GitHub. Токен Remnawave бессрочный (истекает около 2300 года) и, вероятно, даёт полные права. Перевыпуск бесплатен и **не меняет бота для клиентов**. (R04, раздел 9)
6. **Нет решения о резервных копиях базы самой панели**, хотя по решению 08 «срок подписки знает только Remnawave». Потеря базы панели означает потерю сроков всех клиентов. (R06)
7. **Схема адресов противоречива** (Cloudflare или DNS only, куда приходят уведомления ЮKassa, «файрвол пускает только IP ЮKassa»). При неверной сборке проверку IP ЮKassa можно обойти поддельным заголовком. (R11, раздел 3)
8. **Подделка кнопок (`callback_data`)**: клиент может прислать любые данные кнопки. Каждое действие должно заново проверять, чьё это устройство, заказ или право администратора. (R07)

## 3. Противоречия и риски в уже принятых решениях

1. **Cloudflare и адреса — три несовместимые версии.**
   - Задача 07: уведомления ЮKassa идут на `pay.ts-proxy.com` (DNS only, Let's Encrypt), «файрвол пускает только IP ЮKassa».
   - `docs/server-setup.md` §5: `bot.ts-proxy.com` через прокси Cloudflare, сервер принимает **только IP Cloudflare**, настоящий IP берётся из `CF-Connecting-IP`.
   - `docs/server-setup.md` §8: уведомления ЮKassa настроены на `https://bot.ts-proxy.com/...`, то есть через Cloudflare. Это противоречит задаче 07, и тогда сервер увидит IP Cloudflare, а не ЮKassa.
   - **«Файрвол пускает только IP ЮKassa» на уровне `ufw` невозможен**: `ufw` различает IP и порт, но не имя сайта. Порт 443 общий для панели, страницы подписки, сайта, бота и, возможно, ноды. Ограничение по IP делается в веб-сервере (`allow`/`deny` в блоке `pay.`) или в FastAPI.
   - Если Cloudflare проксирует хотя бы один адрес, а сервер доверяет `CF-Connecting-IP`, то любой, кто обратится к серверу напрямую по IP (а он публичен из-за DNS only), подставит в заголовок `CF-Connecting-IP: 185.71.76.1` и пройдёт проверку «IP ЮKassa». Само по себе это не даёт денег (зачисление всё равно идёт после `GET /v3/payments/{id}`, R08), но ломает первую линию защиты.
   - **Предложение (вариант А, рекомендую):** раз настоящий IP всё равно публичен, прокси Cloudflare на этом сервере почти ничего не даёт, кроме путаницы. Все адреса этого сервера — DNS only; сертификаты Let's Encrypt; IP отправителя всегда берётся из соединения; Telegram — по `secret_token` (и, по желанию, по IP Telegram); ЮKassa — по IP в блоке `pay.` и по перезапросу в API. Вариант Б — оставить Cloudflare для `panel.` и `bot.`, но тогда для этих имён пускать на сервер **только** IP Cloudflare (в веб-сервере) или включить Authenticated Origin Pulls. Выбор — за владельцем (задача 07).
   - Отдельно: если на этом же сервере нода с Reality на TCP 443, веб-сервер стоит **за** Xray (типичная схема установщиков: Reality отдаёт «чужой» трафик в nginx через сокет). Тогда реальный IP клиента приходит через `proxy_protocol`, и это нужно настроить явно, иначе все запросы будут «с 127.0.0.1», а проверка IP ЮKassa перестанет работать. Проверить при разведке.

2. **«Вебхуки Remnawave — на локальный адрес бота»** (`server-setup.md` §5). Панель работает в Docker, а `127.0.0.1` внутри контейнера — это сам контейнер, не сервер. Варианты: бот слушает адрес моста Docker (например `172.17.0.1:8080`) и пускает только сеть Docker; или вебхук идёт через веб-сервер на внутреннее имя. **Нельзя** «для простоты» слушать `0.0.0.0:8080`: с учётом R09 порт может оказаться открыт наружу. Обращение бота к API панели по `127.0.0.1:<порт>` в обход веб-сервера может требовать заголовков `X-Forwarded-Proto: https` и `X-Forwarded-For` (так панель отличает доверенный прокси) — сверить с документацией версии 3.x при обновлении.

3. **«Срок подписки знает только Remnawave»** (08) и льготный период (09). Как только бот добавляет 3 льготных дня в Remnawave, панель перестаёт знать «оплачено до». Бот различает это по полю «льготный период начался». Это работает, но хрупко (R20). Компенсация, ручная выдача и льготный период смешиваются в одном `expireAt`. Предложение — в разделе 7.5.

4. **Задача 05 расходится с 04 и 09.** В 05: «при продлении новый срок считается от даты окончания подписки, а не от оплаты»; в 04 (поправка владельца) и 09: в льготный период — **от момента оплаты**. Чеклист следует 04. Нужно поправить формулировку в 05, чтобы разработчик не взял неверное правило.

5. **Документы ещё про Cardlink.** В `docs/checklist.md`: «Cardlink вернул на `/paid`», «Оплатить по СБП», «подпись прошла», «Поддельное уведомление (неверная подпись)»; в `map.md` для задачи 04 — «только СБП». У ЮKassa подписи нет, поэтому тест подделки должен звучать так: «уведомление не с IP ЮKassa / платёж с таким id не найден / сумма не совпала → не засчитано». Иначе тесты будут проверять несуществующую защиту.

6. **«Токены не перевыпускаем, бот остаётся тем же»** (map). Перевыпуск токена через @BotFather (`/revoke`) **не меняет** ни бота, ни его @username, ни чаты с клиентами: меняется только строка в `.env`. Подробно — раздел 9.

7. **«Вся переписка хранится бессрочно»** (16) и «месячные копии бессрочно» (08) противоречат политике обработки ПДн, которую агент будет писать для сайта (12): там придётся указать цель и срок хранения, а клиент вправе потребовать удаления (152-ФЗ). R14.

8. **«Отклонённые поддельные уведомления» в бессрочном «Журнале событий»** (18). Это канал засорения базы: флуд поддельными запросами пишет в вечную таблицу. Логично писать первое событие и счётчик, а остальные склеивать (R29).

9. **`remnawave/backend:3` в чеклисте обновления** — это плавающий тег мажорной версии. Пакет `remnawave-api` строго привязан к версии панели (3.4.5 → панель ≥3.4.4), поэтому следующий `docker compose pull` может незаметно сломать бота (R25). В чеклисте ставим точную версию.

10. **Правило Telegram о цифровых товарах** (17, 19). Владелец выбрал ЮKassa в боте, исследование нашло прямой запрет (§6.2). Это не уязвимость, но это **риск доступности**: если бота удалят, связь со всеми клиентами пропадает, а новый бот не может первым написать тем, кто его не запускал. Нужно явное «риск принят» и запасной канал (R26).

11. **Тесты на боевой панели** (11): защита `dev_` и squad `test` живёт в коде тестового клиента, а токен у него — боевой и полный. Ошибка в коде или кража с Mac бьёт по живым клиентам (R24).

12. **`.gitignore` закрывает только `.env`.** `bot.py` и `rem.py` с токенами сейчас не отслеживаются git, но и не игнорируются: один `git add .` перед созданием репозитория на GitHub, и токены окажутся в истории навсегда.

## 4. Модель угроз

Кто реально может атаковать маленький прокси-сервис:
- **Случайные сканеры и боты** — постоянно перебирают SSH, ищут открытые панели, порты Docker и `/.env`. Вероятность — почти 100%. Цели: R03, R09, R10.
- **Хитрые клиенты** — модифицированный клиент Telegram, подделка кнопок, попытки получить доступ бесплатно, фермы аккаунтов, перепродажа ссылки. Цели: R07, R17, R35.
- **Тот, кто узнал адрес бота** (из логов, сканирования сертификатов: имена из Let's Encrypt публикуются в журналах Certificate Transparency, так что `pay.ts-proxy.com` и `bot.ts-proxy.com` станут известны сразу после выпуска сертификата). Цели: R01, R08.
- **Укравший секрет** — с Mac, из GitHub, из резервной копии, из переписки. Цели: R04, R15.
- **Сами администраторы** — ошибки, а не злой умысел. R22.
- **Государство и провайдеры** — блокировка IP, домена, замедление Cloudflare. R13.
- **Хостер** — отключение сервера по жалобе на трафик. R13.

### 4.1. Поддельные уведомления ЮKassa

Подписи у уведомлений нет. Поэтому уведомление — это только **повод проверить**, а не факт оплаты.

Порядок обработки:
1. Веб-сервер в блоке `pay.` пускает только IP ЮKassa из документации (`185.71.76.0/27`, `185.71.77.0/27`, `77.75.153.0/25`, `77.75.156.11`, `77.75.156.35`, `77.75.154.128/25`, `2a02:5180::/32`). IP — из соединения, не из заголовка.
2. Из тела берём **только** `object.id`. `metadata`, сумму и статус из тела не используем.
3. Ищем заказ по сохранённому `payment_id`. Нет такого — ответ 200, запись в счётчик подделок, **без запроса в API** (иначе флуд случайными id превращается во флуд запросами к ЮKassa от нашего имени).
4. `GET /v3/payments/{id}` с нашим ключом. Засчитываем, только если одновременно: `status == "succeeded"`, `paid == true`, `amount.value` равно сумме заказа как `Decimal`, `amount.currency == "RUB"`, `metadata.order_id` совпадает с заказом, `test` совпадает с режимом (`false` в бою, `true` в тестовом магазине).
5. Отвечаем 200, только когда результат **записан в БД**. Если упала наша база — 500, и ЮKassa повторит (до 24 часов).

`payment.canceled` тоже перепроверяем: поддельная «отмена» не должна закрыть оплаченный заказ.

### 4.2. Поддельные вебхуки Remnawave

- Подпись `X-Remnawave-Signature` — HMAC-SHA256 от **сырого тела** (байты до разбора JSON) с ключом `WEBHOOK_SECRET_HEADER`. Сравнение через `hmac.compare_digest`.
- Время входит в тело (`timestamp`), поэтому старое подписанное тело можно прислать повторно. Защита: отвергать события старше, например, 10 минут, и главное — **считать вебхук сигналом**: перечитать пользователя через API и действовать по текущему состоянию. Тогда повтор или запоздавшее событие ничего не ломают.
- Эндпоинт вебхуков Remnawave доступен только из сети Docker (не публикуется наружу).

### 4.3. Поддельные кнопки (`callback_data`)

`callback_data` присылает приложение клиента, и модифицированный клиент присылает что угодно (до 64 байт). Правила:
- **Админские действия** проверяют `from_user.id in ADMIN_IDS` в каждом обработчике (лучше одним фильтром на весь роутер админки), а не «кнопку показали только администратору».
- **Объекты клиента** не берутся из кнопки как есть. «🗑 Удалить устройство» — бот получает список устройств **прокси-аккаунта нажавшего** и удаляет `hwid`, только если он в этом списке. «Проверить оплату» — заказ должен принадлежать нажавшему.
- **Тариф** — только по id из `tariffs.yaml`; скрытый «Тест 15 ₽» создаётся только для администратора, и проверка стоит в сервисе создания заказа, а не только в клавиатуре.
- **Возврат** — условия (30 дней, раз в полгода) проверяются заново и при нажатии клиента, и при «✅ Одобрить».
- Использовать фабрики `CallbackData` aiogram с типами (pydantic отбросит кривые данные).
- В наброске есть пример того, как нельзя: `check_<invoice>_<months>` берёт число месяцев из кнопки. В новом коде так не делаем (это уже правило 12 `python-rules.md`).

### 4.4. Чужой Telegram ID

`from_user.id` в апдейте, который пришёл от Telegram, подделать нельзя. Подделать можно **сам апдейт**, если webhook не защищён (R01). Поэтому `secret_token` — главная мера всей модели угроз. Дополнительно:
- Поиск в админке по `@username` опасен: имя можно сменить, и его займёт другой человек. Действия (выдача, сброс) — по ID, после показа карточки клиента.
- Перенос подписки на «новый аккаунт» — только с подтверждением (R36).
- `start`-параметр из `return_url` (`t.me/<бот>?start=paid_<n>`) может открыть кто угодно. Он только запускает проверку **своего** заказа нажавшего.

### 4.5. Перебор и флуд

- **Telegram:** ограничение частоты на клиента в middleware (например, не больше 1 действия в секунду и 30 в минуту; поддержка — уже решено «10 в минуту»). Тяжёлые действия (создание платежа, проверка оплаты, список устройств) — отдельный лимит и переиспользование результата.
- **Платежи:** один ожидающий платёж на клиента и тариф (уже решение 04). Новый платёж для другого тарифа не чаще раза в N секунд.
- **Веб:** `limit_req` в веб-сервере для `/health` и вебхуков; тела запросов ограничены по размеру (например, 64 КБ).
- **Пробный период:** уникальный индекс в БД «один пробный на Telegram ID», а не только проверка в коде. Двойное нажатие не создаёт два аккаунта.

### 4.6. Утечка ссылки подписки

Ссылка = доступ к прокси. Где утекает: скриншоты клиента, пересылка друзьям, перепродажа, переписка поддержки (клиент вставляет ссылку в вопрос — она навсегда в БД и в группе), access-логи веб-сервера (`/sub/<shortUuid>` в адресе), резервные копии.

Меры: перевыпуск ссылки (R17, новое решение); access-лог подписки выключен или маскирован; HWID-лимит 3 (уже решено); страница подписки при включённом HWID не показывает ключи (так устроена панель); в оферте — запрет перепродажи (уже есть).

### 4.7. Кража токенов

Раздел 5 — что где лежит, ущерб и как отозвать. Главное: секреты только в `.env` (права 600) на сервере и в `.env` разработки на Mac; разные токены для разработки и боя; заранее записанный порядок действий «что делать, если утёк X» (раздел 5, последняя колонка).

### 4.8. Взлом сервера

Если сервер взломан под `root`, проиграно всё: панель, бот, `.env`, база. Поэтому защищаем **вход** (R10, R03, R09) и уменьшаем ущерб от взлома **только бота** (R28): бот работает от `tsproxy`, не в группе `docker`, без `sudo`, не может менять свой код. Копии зашифрованы открытым ключом и лежат вне сервера, без права удаления (R15), — даже после полного взлома есть из чего восстановиться.

План на случай взлома: отключить сервер от сети в панели хостера → перевыпустить все секреты из раздела 5 (с другого устройства) → поднять новый сервер из копий → сменить адреса в DNS.

## 7. Надёжность

### 7.1. Двойное начисление (R02)

Три пути зачисления (уведомление, кнопка, фоновая проверка) плюс Stars сходятся в **одну** функцию сервиса «засчитать оплату заказа». Внутри:

1. В одной транзакции SQLite (`BEGIN IMMEDIATE`): `UPDATE orders SET status='paid', paid_at=… WHERE id=? AND status IN ('created','pending')`. Изменилась 0 строк — значит, кто-то уже засчитал, выходим.
2. Победитель рассчитывает **новую дату окончания** чистой функцией `domain/` по текущему состоянию аккаунта и записывает её в заказ (`grant_target_expire_at`) и статус `granting`.
3. Вызов Remnawave: `update_user` с этой датой (плюс лимит устройств, трафик 0, снять тег `TRIAL`), а не `extend +N дней`.
4. Статус `granted`.

Если процесс упал между 3 и 4, повтор видит `granting` с готовой датой. Он перечитывает аккаунт: если `expireAt >= grant_target_expire_at`, то просто ставит `granted`; если нет — ставит дату ещё раз. Ни одного лишнего дня.

Плюс:
- уникальные индексы на `payment_id` ЮKassa и `telegram_payment_charge_id`;
- одна блокировка на клиента (`asyncio.Lock` по ID) вокруг шагов 2–4, чтобы две разные оплаты одного клиента не посчитали дату от одного и того же старого срока;
- SQLite в режиме WAL, `busy_timeout`;
- **одновременно работает только один экземпляр бота** с боевой базой (systemd это обеспечивает; локальный бот никогда не смотрит в боевую базу).

Поле `grant_target_expire_at` — изменение структуры таблицы «Заказы», поэтому по правилу из `map.md` нужно согласие владельца.

### 7.2. Падение между «оплачено» и «доступ выдан»

Решение 04 (повторы каждую минуту 30 минут, потом тревога) хорошее, но повторы должны жить **в базе**, а не в памяти: `attempts`, `next_attempt_at` у заказа и фоновая задача, которая берёт заказы `paid/granting` с наступившим временем. Тогда перезапуск бота посреди повторов ничего не теряет.

Предложение (на согласование, 04): после 30 минут и тревоги **не останавливать** автоматические повторы, а продолжать реже (раз в 15 минут до суток). Администратору легче, если панель поднимется сама ночью.

«Момент оплаты» для расчёта срока (новый клиент, льготный период) — момент, когда бот **выдаёт** доступ, а не `captured_at` из ЮKassa. Если уведомление потерялось на час, клиент не теряет оплаченный час.

### 7.3. Восстановление после простоя бота

- Telegram и ЮKassa сами повторяют до 24 часов, плюс фоновая проверка неоплаченных платежей (решение 04). Всё догоняется.
- Remnawave повторяет только 15 секунд. **Нужна сверка** (R05): раз в 5–10 минут запрашивать у панели аккаунты `tg_*` со сроком в ближайшем окне и с истёкшим сроком и сравнивать с нашей таблицей «Уведомления» и отметкой льготного периода. Это та же функция, что «проверка при старте» из решения 09, только по расписанию.
- Ноды: тот же опрос статуса нод, иначе потерянное `node.connection_lost` означает, что администраторы не узнали о простое и компенсацию не предложили.
- Деплой: остановка с ожиданием текущих запросов (`TimeoutStopSec`), в это время веб-сервер отдаёт 502, и Telegram и ЮKassa повторят позже.

### 7.4. Синхронизация бота и Remnawave

- Аккаунт ровно один: `tg_<telegram_id>`. Одновременное «Попробовать» и «Купить» — второй `create_user` получит 409; его обрабатываем как «найти существующий».
- Кто-то удалил аккаунт руками в панели: сохранённый id указывает в пустоту → `NotFoundError` → создать заново, тревога администраторам (ссылка у клиента сменится).
- Администратор изменил срок руками в панели — бот это переживёт, потому что всегда читает срок из панели. Но в «Журнале событий» этого не будет; правило — менять сроки через админку бота.
- Боевой код отказывается менять аккаунты без префикса `tg_` (зеркально защите `dev_` в тестах). Так ошибка в коде не заденет личные или ручные аккаунты владельца в панели.
- Версии: точный тег панели и точная версия `remnawave-api` (R25). При старте бот проверяет версию панели (`/api/system/metadata`) и громко ругается при несовпадении.

### 7.5. Льготный период: граничные случаи (R20)

Проблемы текущей схемы («бот по событию `user.expired` добавляет 3 дня»):
- **Бот лежал в момент окончания.** Панель за 30 секунд переводит аккаунт в EXPIRED, клиент без доступа, пока бот не поднимется и не сверит. Для платящего клиента это самый неприятный сбой.
- **`extend` у ACTIVE считает от текущего `expireAt`.** Покупка в льготный период по правилу «от момента оплаты» через `extend` даст «конец льготного + N», то есть клиент получит ещё и остаток льготных дней. Значит, дату ставим явно через `expireAt`.
- **Компенсация в льготный период** продлевает `expireAt`, а покупка «от момента оплаты» её затирает. Решить: компенсация в льготный период переносит и отметку «льготный начался», или компенсацию льготным не даём.
- **Напоминания `EXPIRATION_NOTIFICATIONS=[-24,-1]`** сработают и перед концом оплаченного срока, и перед концом льготного (и перед концом пробного). Тексты выбираются по состоянию клиента — тест на каждый случай.
- **Два вебхука подряд** (`user.expired` пришёл дважды) не должны дать 6 льготных дней: отметка «льготный начался» ставится атомарно, как статус заказа.

**Вариант Б (на согласование, 08 и 09):** при каждой оплате ставить в Remnawave сразу `expireAt = оплачено_до + 3 дня`, а «оплачено до» хранить у себя в заказе (или у клиента). Тогда доступ **никогда** не зависит от того, работал ли бот в момент окончания. Напоминания и «льготный период начался» бот считает сам по своей дате. Минус: в приложении клиента (Happ показывает срок из ссылки подписки) будет видна дата на 3 дня позже оплаченной; на странице подписки — тоже. Это можно объяснить в тексте («с запасом 3 дня на продление»). Это меняет решение 08 «срок знает только Remnawave», поэтому только с согласия владельца. Если владелец оставляет текущую схему, то сверка из 7.3 обязательна.

### 7.6. Пробный период

- Покупка в пробный: снять лимит 7 ГБ (`trafficLimitBytes=0`), снять тег `TRIAL`, лимит устройств как у тарифа (R21).
- Пробный закончился через LIMITED (7 ГБ израсходованы) — это «подключался», продлений нет. Тест.
- «Сброс пробного периода» администратором — запись в журнал с причиной.
- «Один раз на ID» — уникальный индекс, а не только проверка.

### 7.7. Компенсация при сбое ноды

- Один инцидент — одна компенсация: у инцидента своя запись и статус, кнопку «Компенсировать» нельзя нажать дважды (двумя администраторами одновременно — тоже).
- «Мигание» ноды (упала и поднялась 10 раз за час) склеивается в один инцидент.
- Решить, что считать сбоем, если нод несколько и упала одна (часть клиентов переключилась сама) — **недостающее решение** для 06.
- Компенсация — тоже через абсолютную дату и с записью, кому начислено, чтобы падение на середине рассылки не дало кому-то двойную компенсацию.

### 7.8. Потерянные уведомления — сводка

| Источник | Если потеряли | Страховка |
|---|---|---|
| ЮKassa | Повторы 24 ч | Фоновая проверка ожидающих платежей + кнопка «Проверить оплату» (решено) |

### 7.9. Часы и часовые пояса

Бот и панель на одном сервере, часы общие. Нужен NTP (`timedatectl` показывает `System clock synchronized: yes`). Всё в UTC (правило 7 уже есть), «по Москве» — только при показе. В Москве нет перехода на летнее время, но тесты с замороженным временем всё равно используют aware-даты. Ежедневный отчёт «в 10:00 МСК» планировщик считает в `Europe/Moscow`, а не в часовом поясе сервера.

## 8. Ошибки администраторов (R22)

- **Рассылка** — предпросмотр и кнопка «Да, отправить N клиентам»; отправка порциями с учётом лимитов Telegram; можно остановить; запись в журнал.
- **Ручная выдача** — по ID, с карточкой клиента и подтверждением; предел, например, 400 дней за раз; запись в журнал.
- **Компенсация** — один раз на инцидент (7.7).
- **Возврат** — бот показывает сумму и номер платежа; отключение подписки после подтверждения; событие `refund.succeeded` от ЮKassa сверяется с одобренным запросом (возврат без запроса → тревога).
- **`tariffs.yaml`** — при старте проверка: цена > 0, дни из разрешённого набора, скидки в разумных пределах, скрытый тариф помечен явно. Опечатка «15» вместо «150» не пройдёт незамеченной: бот откажется запускаться или пошлёт тревогу.
- **Деплой** — копия базы перед миграцией (уже решено), понятный откат; не выкатывать в часы пик.
- **Боевые и тестовые ключи** — бот при старте проверяет, что боевой бот работает с боевым магазином (`test == false` в ответах), а тестовый — с тестовым.
- **Режим fake** (R23) — не запускается рядом с боевым токеном.
- **Администраторов двое** — у каждого свой вход в панель и на сервер (не общий пароль), чтобы журнал показывал, кто что сделал, и доступ одного можно было отозвать.

## 9. Старые токены из наброска — оценка решения «не перевыпускать»

**Факты:**
- `BOT_TOKEN`, `REMNAWAVE_TOKEN` и адрес панели записаны открытым текстом в `bot.py`; `REMNAWAVE_TOKEN` — ещё и в `rem.py`.
- Эти же значения есть в журналах сессий Claude Code на Mac (`~/.claude/projects/...`): набросок читался агентом, и содержимое файлов сохраняется в истории сессий. Значит, токены также передавались в контексте модели.
- `bot.py` и `rem.py` не отслеживаются git (это хорошо), но и не внесены в `.gitignore`. Репозиторий на GitHub только планируется.
- Токен Remnawave бессрочный (истекает около 2300 года), проверка 03 подтвердила, что он рабочий. Ограничены ли его права — неизвестно; скорее всего, это полный доступ.
- Неизвестно, показывался ли набросок кому-то ещё и где он мог побывать (мессенджеры, облака). Папка `~/Documents` на Mac может синхронизироваться в iCloud — проверить.

**Оценка.** Вероятность того, что токены уже у кого-то есть, **низкая**, но ненулевая и **непроверяемая**. Ущерб при утечке токена Remnawave — **критический** (вся панель), токена бота — **высокий** (перехват бота и фишинг клиентов). Цена перевыпуска — **около 5 минут и ноль последствий для клиентов**:
- новый токен бота (`/revoke` у @BotFather) оставляет того же бота с тем же @username и всеми чатами; клиенты ничего не замечают;
- новый токен Remnawave создаётся в панели за минуту, старый удаляется.

Решение «бот остаётся тем же», похоже, исходит из того, что перевыпуск меняет бота. Это не так.

**Рекомендация (на согласование):**
1. При запуске нового бота перевыпустить **оба** токена. Новые значения сразу в `.env` на сервере, не в чат и не в файлы с кодом.
2. Создать **отдельный** токен Remnawave для разработки (R24).
3. До создания репозитория на GitHub: стереть значения токенов из `bot.py` и `rem.py` (или перенести набросок в архив без секретов) и добавить оба файла в `.gitignore`. Поставить поиск секретов (`gitleaks` или аналог) в `pre-commit`.
4. После перевыпуска старые значения в журналах сессий и в iCloud становятся безвредными, отдельно их чистить не нужно.

Если владелец всё же не хочет перевыпускать — минимум пункт 3 обязателен, и токен Remnawave нужно хотя бы заменить после обновления панели до 3.x (заодно проверить, умеет ли 3.x ограничивать права токена).

## 10. Данные

**Что хранится у нас:** Telegram ID, @username, имя; заказы и платежи (без карт — только id платежа и сумма); пробный период; уведомления (90 дней); «Журнал событий» (бессрочно); обращения и **вся переписка** (бессрочно), файлы как `file_id`.

**Что хранится в Remnawave:** аккаунты, сроки, ссылки, устройства (модель, ОС, user agent, IP запросов подписки), статистика трафика. На нодах — возможно, access-логи (R30).

**Риски и меры:**
- **152-ФЗ** (R14, вопрос юристу вместе с задачей 17): Telegram ID плюс имя плюс переписка — это персональные данные. Есть требование хранить ПДн граждан РФ при сборе в базах на территории РФ (локализация), а сервер зарубежный. Срок хранения должен соответствовать цели, клиент вправе требовать удаления, оператор ПДн подаёт уведомление в РКН. Агент не юрист — это вопрос к консультации, но решение «хранить переписку вечно» стоит пересмотреть уже сейчас.
- **Предложение (на согласование, 16 и 08):** переписку обращений хранить, например, 3 года после последнего сообщения клиента (споры с платёжкой, возвраты — до 3 лет, как и окно возвратов ЮKassa), затем удалять; удаление по запросу клиента — командой администратора; месячные копии хранить не вечно, а, например, 3 года. «Журнал событий» по заказам (доказательство оказания услуги) хранить столько же.
- **Маскирование в переписке:** если клиент прислал ссылку подписки, сохранять её замаскированной (как в логах), а в тему пересылать как есть.
- **Доступ к базе:** файл SQLite и файлы `-wal`/`-shm` — владелец `tsproxy`, права 600, папка 700. Никто, кроме `tsproxy` и `root`, не читает.
- **Копии:** `sqlite3 .backup` (или `VACUUM INTO`) без остановки бота → сжатие → шифрование открытым ключом `age` → три места (сервер, тема «💾 Бэкапы», облако). В облаке — ключ только на запись, без удаления. Раз в месяц — пробное восстановление (уже в плане). Копия `.env` бота и панели — отдельно, тоже зашифрованная, не в тему Telegram.
- **Копии панели** (R06) — ежедневный дамп Postgres панели тем же путём. Сейчас его нет ни в одном решении.
- **Логи** (решение 18 хорошее, дополнения R16): не логировать тела запросов и уведомлений; логгеры `httpx` и `httpcore` — не ниже WARNING; access-лог веб-сервера для `/sub/` выключить; путь webhook без токена; тексты тревог тоже без секретов и полных ссылок. Автотест «секретов нет в логах» (уже решено) прогонять и по тексту тревог.
- **Тема «💾 Бэкапы»** — файлы там зашифрованы, но участники группы могут их скачать; ключ расшифровки у них не лежит.

## 11. Сервер

Состояние неизвестно, всё ниже — для разведки (раздел 0 `server-setup.md`) и настройки.

- **SSH (R10):** ключи ed25519 с паролем → проверка входа в новом окне → `PasswordAuthentication no`, `PermitRootLogin no`, `KbdInteractiveAuthentication no` → fail2ban. Отдельный пользователь с `sudo` для каждого, кому нужен вход. Агенту доступ, если понадобится, — под этим пользователем и с подтверждением каждой команды (как уже написано в плане).
- **Файрвол (R09):** `ufw` открывает 22, 80 (выпуск сертификатов), 443 и порты нод. **Проверить снаружи** (с Mac через `nmap` или онлайн-сканер), что не видно портов Docker (`3000`, `5432`, `6379` и подобных). Публиковать контейнеры как `127.0.0.1:порт:порт`.
- **Сервер по умолчанию:** запрос на IP сервера без известного имени сайта — закрыть соединение (`return 444` в nginx или аналог в Caddy), а не показывать панель.
- **Панель (R03):** доступ к админке только через SSH-туннель (`ssh -L`) или по белому списку IP; если установщик ставил защиту по секретному пути или cookie — оставить; второй фактор при входе, если версия панели его поддерживает; страница подписки — отдельное имя, админка через неё не открывается.
- **Пользователи и права:** `tsproxy` без пароля и входа; код `/opt/tsproxy` принадлежит пользователю деплоя (для `tsproxy` только чтение); `/var/lib/tsproxy` — `tsproxy`, 700; `.env` — 600 (или `root:tsproxy` 640). `tsproxy` не в группе `docker` (группа `docker` = права `root`).
- **systemd (R28):** `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ReadWritePaths=/var/lib/tsproxy`, `ProtectHome=yes`, `PrivateTmp=yes`, `MemoryMax=` (например, 512M, чтобы бот не отнял память у панели), `Restart=always`. Бот слушает только `127.0.0.1` и, если нужно для вебхуков панели, адрес моста Docker.
- **Обновления:** `unattended-upgrades` для обновлений безопасности; перезагрузка для ядра — вручную в спокойное время или по расписанию ночью; после перезагрузки поднимаются панель (политика перезапуска Docker) и бот (`enable`) — проверить один раз.
- **Место на диске и память:** свободно ~2,2 ГБ памяти; тревога бота, если диска меньше 15%; журнал systemd с ограничением размера (`SystemMaxUse=`), не только по сроку.
- **Время:** NTP включён.
- **Cloudflare и прямые адреса:** раздел 3, пункт 1. Сертификаты для имён DNS only — Let's Encrypt через HTTP-01 (порт 80) или DNS-01 с токеном Cloudflare только на `Zone:DNS:Edit` этой зоны.
- **Панель и бот на одном сервере:** допустимо для 30 клиентов, но главный риск — **нода на том же IP** (R13). Если при разведке окажется, что нода здесь же: блокировка IP в РФ или жалоба хостеру положит и бота, и приём оплат, и сайт. Тогда лучше вынести ноду (или «бот + панель + сайт») на отдельный недорогой сервер. Это решение задачи 07.
- **Ноды:** проверить, что access-лог Xray выключен или не пишет адреса назначения (R30); включить Torrent Blocker, чтобы снизить шанс жалоб хостеру; закрыть `vless_ws` 8080 без TLS (R31, уже в `owner-todo.md`).
