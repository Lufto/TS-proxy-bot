# Два сервера, на каждом рабочие подключения

Status: ready-for-agent
Карта: [map.md](map.md) · задачи: [issues/](issues/)

## Проблема

Клиент открывает приложение (чаще всего Happ), выбирает подключение из подписки — и интернет не открывается. 2026-11-20 выяснилось, что прямые подключения основного **сервера** («Германия») не работают из России. В подписке у каждого клиента 8 **подключений**, все включены, и клиент не знает, какие из них живые: перебирает по одному или решает, что прокси не работает вовсе.

Что известно:

- Маскировка Reality основного смотрит в мёртвый `nani.alttux.site` (с ~2026-11-08, todo п. 37): любой, кто постучится без ключа, получает обрыв вместо настоящего сайта — сервер легко распознать.
- У «Германии 2» нет **доменного подключения**: если её IP заблокируют, у неё не останется запасного пути.
- «Германия 2» есть у всех 40 клиентов (`Default-Squad`), но онлайн на ней 0, на основном — 8. Непонятно: не проходят подключения или клиенты не обновили подписку.
- Оба сервера в одной подсети одного хостера (130.78.12.x).
- Проверить «работает ли из России» с Mac агента нельзя: он сам ходит через наш прокси.

## Решение

На каждом из двух серверов у всех клиентов есть минимум одно **прямое** подключение (Reality) и одно **доменное** (через Cloudflare), и оба проверены из России. Подключения, которые из России не работают, выключены в панели (не удалены), поэтому клиент видит в подписке только рабочие.

Порядок работ:

1. **Проверка из России** — для каждого подключения и адреса сервера: проходит ли TCP, проходит ли TLS-рукопожатие с SNI подключения, есть ли трафик. Это отличает «заблокирован IP» от «режут по признакам Reality». Плюс проверка владельцем с телефона: мобильный интернет и домашний Wi-Fi.
2. **Скрыть нерабочие** — выключить хосты в панели по итогам проверки; хосты до изменения — в `~/Backups/`.
3. **Маскировка основного** — живая цель Reality вместо `nani.alttux.site`, если IP не заблокирован целиком. Если заблокирован — решение по пункту «IP заблокирован» (см. «Решения, которые ещё предстоит принять»).
4. **Доменное подключение для «Германии 2»** — по образцу «домен 1/2» основного.
5. **Маскировка «Германии 2»** — по итогам п. 3.
6. **Повторная проверка из России** всех включённых подключений после изменений.

## Решения о реализации

- **Термины** — по `GLOSSARY.md`: **сервер** («Германия» — основной, «Германия 2»), **подключение** (сервер + способ, хост в панели), **доменное подключение** (через Cloudflare по нашему домену). В тексте для клиента и владельца — только эти слова; «хост», «инбаунд» — в технических заметках.
- **«Нерабочее» = не открывает интернет из России.** Источники: check-host.net (российские точки — TCP до порта; TLS-рукопожатие с SNI подключения) и владелец с телефона (мобильный оператор + домашний Wi-Fi). Подключение нерабочее, если не прошло хотя бы на одном мобильном операторе России; спорные случаи — к владельцу.
- **Скрываем выключением хоста** в Remnawave (переключатель), не удалением. Копия хостов до изменения — в `~/Backups/<дата>/`. В задаче записывается: что выключено, по какой проверке, как вернуть.
- **Права агента на серверах.** Чтение и тесты — без спроса. Выключение подключений, которые проверка показала нерабочими, — без спроса (владелец, 2026-11-20). Всё остальное (маскировка, новые инбаунды, хосты, правила подписки, закрытие портов) — после «ок» владельца на каждое действие.
- **Маскировка Reality** — живая цель, не связанная с `ts-proxy.com`. Предпочтение — self-steal: нейтральный домен с A-записью на IP самого сервера (серое облако), настоящий сертификат, сайт на этом же сервере за Xray (Xray на 443 отдаёт не-Reality соединения сайту). Конкретный домен и место сайта решаются в задаче 04; «Германия 2» — по итогам 04, в задаче 06. Делаем только если проверка показала, что IP не заблокирован целиком.
- **Доменное подключение «Германии 2»** — по образцу основного: поддомен в зоне Cloudflare, способ ws или xhttp, TLS до Cloudflare на 443 (SSL Flexible для поддомена, Origin Rule на порт инбаунда), хост с `security=tls`, SNI/host = поддомен, `fp=chrome`, `alpn` как у «домен 1/2». Владелец делает записи и правила в Cloudflare, агент — инбаунд, хост и проверку после «ок». Конкретика — задача 05.
- **Смена маскировки ломает подключения у клиентов, не обновивших подписку.** Поэтому перед сменой — проверить, что у них остаётся хотя бы одно рабочее подключение (доменное не зависит от маскировки Reality), и только потом менять.
- **Названия** — уже утверждённые: «🇩🇪 Германия - подключение 1…4», «🇩🇪 Германия 2 - подключение 1…2», «🇩🇪 Германия - подключение домен 1…2»; новое доменное «Германии 2» — «🇩🇪 Германия 2 - подключение домен 1». Технические подробности — в тегах хостов (`SRV:…`, `VIA:CLOUDFLARE`, `SNI:…`), не в видимых полях (Happ показывает `serverDescription`).
- **Порядок в подписке** сейчас: Германия → Германия 2 → домены. Меняется ли он — решается после проверки (рабочие вверх).
- **Код бота не меняется.** Бот выдаёт ссылку на подписку, состав подписки определяет Remnawave. Если для клиентов понадобится сообщение («обновите подписку») — это рассылка `/broadcast` и отдельное решение владельца.
- **Скрипт проверки** — в `ops/` (рядом с `server-hardening`, `remnawave-backup`): берёт список подключений из панели (или из подписки тестового аккаунта), запускает проверки check-host.net с российских точек, печатает таблицу «подключение → TCP / TLS → вывод». Секреты — из окружения, не в репозитории.

## Решения о проверке

- **Одна граница проверки — подписка клиента, проверяемая из России.** Проверяем то, что реально получает клиент: список подключений из подписки и проходят ли они из российской сети. Не проверяем внутренности (конфиг Xray, правила Cloudflare) отдельно — они верны, если подключение проходит.
- **Два уровня этой границы:**
  1. Автоматический — скрипт в `ops/` через check-host.net: TCP до порта и TLS-рукопожатие с SNI подключения, с нескольких российских точек. Повторяется одной командой до и после каждого изменения.
  2. Ручной — владелец с телефона в Happ по чеклисту агента: открывается ли сайт, примерно какая скорость, на мобильном интернете (оператор) и Wi-Fi. Только он подтверждает «работает» до конца: check-host не проходит рукопожатие Reality с ключом клиента.
- **Дополнительно с сервера (только чтение):** трафик и онлайн по инбаундам за сутки — показывает, ходят ли клиенты через подключение на деле.
- **Хорошая проверка** отвечает на вопрос клиента «открывается ли интернет через это подключение из России», а не «правильно ли записан конфиг».
- **Прежний опыт:** проверка клиентом Xray с «Германии 2» и скрипт `sites.sh` (2026-11-01, `.scratch/archive/tsproxy-bot/issues/37-podklyucheniya-i-maskirovka.md`) — проверяли «интернет есть / Claude отвечает / скорость», но не из России. Тесты бота (`bot/tests/`) не затрагиваются.
- **Готово**, когда по каждому серверу таблица проверки показывает минимум одно прямое и одно доменное подключение, прошедшие и check-host, и проверку владельца с мобильного интернета; все остальные включённые подключения тоже проходят.

## Вне задачи

- Третий сервер у другого хостера — следующая карта, после того как два нынешних заработают (владелец, 2026-11-20).
- Российский VPS как постоянная точка проверки и мониторинга.
- MTProto-прокси `mtg` на «Германии 2».
- Изменения кода бота и его текстов.
- «Россия напрямую» (правила маршрутизации в приложениях) — сделано 2026-11-01, не трогаем.
- Скорость канала у хостера — не исправить с нашей стороны.

## Решения, которые ещё предстоит принять

Из «Not yet specified» карты; каждое решается по ходу, по фактам проверки:

- **Основной заблокирован по IP** (а не по признакам Reality): новый IP у хостера, оставить только доменные или другое.
- Одинаковый ли набор способов на обоих серверах и сколько прямых подключений держать (сейчас 4 и 2; отличаются только упаковкой внутри туннеля).
- Как довести изменения до клиентов, которые не обновляют подписку.
- Когда закрыть старые порты 8080/2052 без TLS.
- Отпечаток `fp`: `randomized` у основного, `chrome` у «Германии 2».
- Порядок подключений в подписке после изменений.
