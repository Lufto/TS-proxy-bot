# 01: Оплата СБП — уведомления Platega и зачёт

**What to build:** владелец знает, что по СБП нельзя получить дни без оплаты, засчитать платёж дважды, засчитать чужой или неверный платёж. Проверены: подлинность уведомления Platega (подпись, бот сам переспрашивает статус), сверка суммы, заказа и клиента с ответом платёжки, повтор уведомления, уведомление о старом/отменённом/чужом заказе, «🔄 Проверить оплату», фоновая проверка и повторное «Купить» одновременно с уведомлением, признак тестового кабинета Platega в бою.

## Находки

Разобрано по коду (`web/payments.py`, `services/payment_checks.py`, `services/crediting.py`, `integrations/platega.py`, `services/orders.py`) и по имеющимся автотестам — их 90, они уже покрывают каждый сценарий задачи: подделка без ключей (400, к платёжке не идём), чужой и выдуманный номер платежа, повтор уведомления, «отменён» по оплаченному заказу, поздняя оплата отменённого, кнопка «Проверить оплату» по чужому заказу, «Купить» одновременно с уведомлением, два одновременных зачёта, сумма не по тарифу, платёж другого заказа, тестовый платёж в бою. Новых тестов не понадобилось: 🔴 в коде нет.

Как устроено (почему лазейки нет): зачёт — один `UPDATE … WHERE заказ ждёт оплаты AND payment_id = …`, второй раз он меняет 0 строк; перед ним бот спрашивает Platega сам и сверяет статус, номер платежа, номер заказа (`payload`), валюту и сумму; цена и дни — только из `config/tariffs.yaml`; пустой `PLATEGA_SECRET` бот не примет (не стартует).

### Для задачи 10 (проверки снаружи, на `https://bot.ts-proxy.com`)

- `POST /payments/notification` без заголовков, с телом `{"id":"x","status":"CONFIRMED"}` → ждём 400, одна склеенная тревога «подделка».
- То же с неверными `X-MerchantId` / `X-Secret` → 400.
- Тело больше 64 КБ (заявленный `Content-Length` 70000) → 413, тело не читается.
- `GET /payments/notification` → 405.
- Мусор (не JSON, 10 КБ) → 400.
